# M1 — durable extraction execution

Implementation boundary: a disabled-by-default Core `ExtractionQueue` and
standalone extraction worker, using PostgreSQL staging and the existing isolated
whole-original parser. M0 regularly merged in PR56 as `e297376938ad12fa629bb595b50a43c0320d1207`
after full run `41598413767`; exact-source promotion verification passes for
`7fcb1053796db347cc3103d42b540e86390a9b0c`. M1 uses that actual merged main.
PDF partitioning, assembly/publication, UI and native
parallel-worker lifecycle remain M2/M3/M9 work.

The explicit `enabled=True` Core producer interface can hand off a queued source
version into one whole-document unit. In the same short transaction it reconciles
the run and finishes only that version's still-queued legacy extraction job.
Otherwise the normal source handler and serial scheduler remain unchanged.
Completed M1 results are private staging with run state `assembling`; they are
never current documents, citations, source-sync receipts or search results.

M1 accepts trusted native Core actors only. Session/delegated handoffs fail closed
before writing: persisting an access-token verifier or stripping its binding would
silently enlarge authority. Durable OAuth handoff needs a separate reviewed Core
grant binding before exposing this interface through HTTP/MCP. No new tool or
connector scope is introduced by M1.

Schema 0024 adds space/version-bound runs and units, bounded result columns,
per-attempt UUID tokens, monotonic fences, three-attempt budgets, DB-clock lease
deadlines, due-work indexes and current-writer protocol triggers. The producer
Core candidate is 0.37.0; the released consumer pin/lock remains untouched. Upgrade
adds empty tables, without reindexing or queuing old content. Downgrade requires
the established backup/restore procedure.

All queue mutations use short transactions and existing content/authority lock
ordering. Parsing and original hash verification happen after the claim commits
and releases its connection. Completion rechecks source identity/generation,
persisted membership, deadline and token/fence. Source deletion, generation retry,
retirement and bounded cleanup cancel/fence results. Staging expires by the
earlier of version creation + 24 hours or run creation + 24 hours; retries never
extend it. Cleanup also runs through ordinary source maintenance when opt-in work
is disabled. Successful results survive restart, but never expiry/supersession.

Acceptance: actual PostgreSQL competing claimants, process death/reclaim,
stale/duplicate completion, durable result reconciliation, transient/terminal
failures, parser lock/connection observations, role/space denial, cancellation,
expired staging, source replacement/deletion, protocol/FK constraints and repeated
migration from schema 0023. Preserve M0 and ordinary queue tests. Independent
packaging and full Debian/Rocky gates are required; publication, consumer adoption
and production deployment remain separate operations.

## Producer use

Use the documented explicit local-Core development setup and a disposable
schema-0024 database. Obtain the native actor through the existing trusted
`AccessService`; requests cannot construct a native handoff by removing a session
or OAuth binding. Select the exact intended space:

```python
from czero_core.extraction_queue import ExtractionQueue

queue = ExtractionQueue(database, access, originals, enabled=True).in_space(space_id)
run = queue.enqueue(native_actor, version_id, expected_generation=1)
status = queue.status(native_actor, run['id'])
```

The version must still be queued with its original present. A concurrent legacy
worker can win first; a conflict stops the handoff instead of repeating a write.
Identical uncertain enqueue/complete replies reconcile by generation, manifest,
lease token and result checksum. Cancel through `queue.cancel` while authorized.
Manual failed-unit retry and publication are M2 operations, not implicit fallbacks.

For a separately invoked one-shot worker, use `CZERO_EXTRACTION_UNITS=1 python -m
czero_app.extraction_worker` with the normal database, source directory, issuer and
owner configuration. It starts no schedule, does no model work and contacts no
identity provider. The disabled default opens no database. Never enable it on an
ordinary instance as a substitute for M2 publication or producer release gates.

Run `tests/unit/test_extraction_units.py`, `tests/integration/test_extraction_queue.py`
and `tests/integration/test_extraction_migration.py` alongside the M0 and existing
source/job regressions. At this candidate checkpoint the focused combined selection
passes 53 cases on real disposable PostgreSQL, including real process death. The
actual opt-in app CLI additionally passes a subprocess/configuration test. The
independent wheel and source installations also run `core_extraction_probe.py`;
the full Python/PostgreSQL/packaging selection is running in a disposable Python
3.12 container because the host workspace quota cannot hold another environment.

The first container run passed 2,570 cases, including both independently installed
wheel/source probes. Five unrelated evaluation-control tests failed Git's copied
checkout ownership check: `cp -a` retained the host UID. Failed evidence is retained.
The container checkout's owner is corrected without changing Git configuration
or any test; all 28 evaluation-control cases pass on rerun (11.00 seconds).
A complete fresh-database rerun is in progress. This is environment repair,
not an acceptance waiver.

`claimed`, `succeeded`, `failed` and `retried` are durable operation counters;
`failed` counts failed attempts and `retried` counts scheduled automatic retries.
They are metadata, not inferred throughput improvements. Only safe states/codes,
IDs, counters and deadlines appear in the bounded summary; staged bodies, original
paths and lease tokens never appear in it or the worker's output.
