# C0 UI and documentation refactor

**Decision record · 21 November 2026.** Use the Nethesis Support application as the reference consumer. The first release test is an operator provisioning the bot’s credentials and the running bot retrieving verifiable knowledge. Focused changes in both repositories are in scope. Delivery ends when both changes are merged, released and verified together on makako.

## Execution order

### 1. Establish a reproducible pair

The C0 maintainer freezes current upstream and the Support maintainer freezes the consumer commit. Record released dependencies, schema, compatible official hosting build, module/app/database image digests, operator entry points and prior backup. Inventory registered applications, DNS, TLS, capacity and directory service through supported NS8 interfaces. Allocate a dedicated C0 instance, Support console hostname and test group on makako. Inventory existing official promotion evidence, including the Support runbook’s hosting baseline `463e393`, and check the installed `czero-custom-app contract` output before applying a manifest. Verify the registry digest and full promotion evidence against that SHA. If the images cannot be verified, obtain a newly promoted contract-1 build before the hosted baseline; the standalone C0 reader tests can proceed on the isolated endpoint. Keep both existing C0 instances available. Use synthetic tickets, unique fixture content in two private spaces, and disposable admin, member and non-member identities. Bind the fixture through a deployment-controlled ticket adapter or a dedicated Freshdesk sandbox with only synthetic tickets. Check destination and permitted egress before setting the console client ID because it starts an indexer over the account’s visible tickets, even in evaluation. Disable notes, classification, notifications and production memory effects; exercise the learning writer only in the disposable Intelligence space. Rehearse first sign-in and one grant reconciliation before enabling the test roster timer.

Build a baseline for each journey from the actual entry point. Record elapsed time, manual lookups, wrong turns and failures. Keep a coverage table with columns for persona, route or command, expected result, browser/transport, fixture versus actual service, evidence and owner. Record before/after screenshots only on screens with synthetic data and safe metadata.

**Exit:** A second run can reproduce the deployment and the first retrieval failure or success from named fixtures. Each test destination resolves to the intended lab service before credentials are provisioned.

### 2. Deliver the bot credential and retrieval journey first

In C0, make Account → API keys answer “what can this key read or change, in which spaces, and until when?” Reuse existing key metadata. Show safe names, permissions, allowed spaces, expiry and revocation state. Present the one-time secret at creation, give storage instructions there, and make replacement and verification discoverable. Distinguish public client IDs from secrets in labels, copy actions and examples.

In Support, retain the existing settings `C0_INSTANCE`, `C0_SPACE_ID`, `C0_API_KEY`, `C0_SUPPORT_INTELLIGENCE_SPACE_ID`, `C0_SUPPORT_INTELLIGENCE_SPACE_READ_API_KEY` and `C0_SUPPORT_INTELLIGENCE_SPACE_WRITE_API_KEY`. Use the existing SDK transport and allowlists for an opt-in live reader check, separate from the existing local `doctor` check. Return only the connection name, intended space, effective permission/result and safe recovery action. Compare the issued scopes and space IDs in C0’s safe key metadata, and verify C0 itself denies an out-of-space read before applying Support’s narrower tool filter. Include a misassigned write-capable key as a failing configuration case. The SDK’s read allowlist alone cannot certify a key was issued as read-only. Align search arguments across console, investigation, learning and benchmark callers. Exercise no results, unavailable service, wrong space, revoked key, rotation and a successful exact read. Verify safe behavior when either optional connection is absent.

**Exit:** A fresh operator can follow one guide from key creation to a proven result in both spaces without inspecting JSON or guessing a permission. Run it twice from clean state and record actual hands-on time separately from indexing and sign-in waits. Aim to complete both reads in ten minutes once an operator has access to the two spaces and secret store. In the negative cases no result from another space appears. Record the deterministic two-connection read separately from a hosted SDK investigation that persists an observed source reference for the synthetic ticket. Have the signed-in console member open that same saved Intelligence reference from the ticket and verify its revision and content hash. Record which ticket and inference services were fixtures and which were live.

### 3. Deliver interactive sign-in, administration and recovery

Use existing OAuth and NS8 identity flows. On the C0 website distinguish signing in, granting an application access and authorizing background work. Restore supported internal destinations through the server’s validated return mechanism. Show the app, account, requested permissions, duration and effect of disconnecting. In Technical clients, distinguish manual registration from verified HTTPS metadata. Display the actual public ID after registration, exact callbacks and permission ceiling. A manual client uses its UUID; a metadata client uses the verified metadata URL. Preserve existing registrations, grants, connected apps, issuer/resource, callback rules and the delegated account inventory used by the host.

Configure the Support test origin, callback, resource, private space, directory and group as trusted deployment settings with production-compatible defaults. Apply them consistently to provenance, enrollment, reconciliation and both HTTPS routes. Support has its own login callback, which currently returns to the root. Bind a validated internal ticket destination to the Support login flow and test first login, expired sessions and rejecting an external or malformed destination. Exercise the permission and roster transitions in the journey table, including disconnect, provider outage and re-enrollment. Use the existing host-side delegation flow for administration; keep personal keys limited to their supported scopes.

**Exit:** A new administrator can enroll the provisioner using the published guide and a new member can open an authorized source. Loss of membership, grant or credential produces a specific recoverable outcome at the first protected request where the change takes effect. Existing installations and clients pass the same compatibility tests after upgrade.

### 4. Make the rest of C0 navigable by task

Inventory all routes and feature-gated panels in the reference website, native NS8 settings, and the linked Support screens. Record which routes to improve, which to retain and test, and which legacy links need redirects. Organize navigation around reading knowledge, connecting tools, managing personal access and administering the workspace. Keep common connection tasks visible and detailed automation or compiler instructions one level deeper.

Walk Home and search → Wiki, source and exact evidence; source upload/replacement and recovery; automatic sources when enabled; tables, projects and exploration; Account and Agents; people, spaces, technical clients and background work. Check navigation back to the originating space, stale evidence, paging and long names. Keep knowledge-reading routes read-only where specified. Preserve existing deep links, space selection, and the clearing of protected data and unfinished forms on identity changes.

Use the installed Nebula components in the Vue 3 website and native NS8 Vue 2/Carbon conventions in module settings. Test English and Italian for the C0 interface and examples, keyboard navigation and focus return, screen-reader naming and announcements, contrast, zoom/reflow, desktop and phone widths, light/dark/system themes. Confirm sign-in and consent also work outside the normal application shell.

**Exit:** Every inventoried route has a disposition and a passed observable check. Each core task is completed by keyboard and on a narrow viewport. Compare first-run timings and manual lookups against milestone 1 and correct any regression.

### 5. Publish task guides alongside each feature

Make the C0 docs index the entry point for “Connect a bot”, “Connect a person or assistant”, “Manage access”, and “Host an application”. Keep the API/MCP reference, architecture and release evidence linked separately. Maintain a credential chooser covering creator, consumer, permissions, selected space, lifetime, rotation/revocation and verification. Write each recipe as prerequisites → actions → expected readback → recovery. Link specific UI errors to the relevant section.

Keep generic credential, OAuth, space and hosting behavior in C0. Keep Support field names, secret references, enrollment, roster recovery, ticket evaluation and deployment steps in the Support runbooks. Restore the externally linked `register-a-public-oauth-client` anchor. Reconcile the current tab names, space audience rules and feature-gated source collection. Check headings and links across both checkouts at the candidate revisions, UI labels against both locales, and example payloads against the released tool schemas. Maintain current screenshots only where the sequence benefits from one.

**Exit:** Someone using the guides in a clean profile can carry out the bot, member and administrator journeys with no author coaching. Record where they hesitated and fix the wording or interface. A renamed heading or invalid example breaks the corresponding documentation check.

### 6. Release, verify and hand over

1. Run C0’s frozen frontend install, `npm run check`, Playwright interactions, published-document checks, real HTTPS/PostgreSQL integration and browser suites. Run Support’s complete pytest suite, container acceptance with `SUPPORT_BOT_TEST_IMAGE`, existing console/roster, SDK separation, effects and recovery tests. Add cross-repository tests specifically for the observed schema, configuration and documentation gaps.
2. Have an independent reviewer examine the credential flows, permissions, destination settings, logs, browser storage and upgrade compatibility. Resolve findings and repeat affected tests. Run full Debian and Rocky native install/upgrade, real IdP, backup and restore acceptance on the exact C0 candidate. Keep exact source, full promotion proof and image scan/build evidence for release.
3. Merge compatible C0 changes first and publish through the project release workflow. Pin the verified C0 artifact in the Support acceptance run. Merge Support and publish its private image. Verify both main SHAs and immutable digests. Release Core separately only if a reusable contract actually changes. Select a fresh candidate and reverify if a source changes after testing.
4. Deploy those exact released artifacts to the dedicated makako instance through NS8 and hosting contract 1. Run every journey above. Verify installed digests, both route identities, readiness, roster freshness, expected citation and Wiki revision, revocation and reconnect, staged write receipt, and post-restart behavior. Record what used a real provider, what used a fixture, and any skipped check with its reason.
5. Rehearse recovery on a disposable restore. Stop the candidate’s writers, restore the matching predecessor image set and verified cold data, confirm checksums, routing, roster and receipts, then re-run the read proof. A backup may reinstate a key revoked after the snapshot. On an isolated route, reapply post-backup revocations, reconcile delegated grants and verify the retired fixture key is denied before opening access. Restore the separately backed-up provisioner ownership state and reconcile it with live revisions. Never run an older Support image against a forward-migrated SQLite volume. Leave the accepted makako pair on its tested release and disposition temporary fixtures and credentials.

**Done:** Linked merged PRs and release identities for both projects; a redacted makako acceptance record with the final image digests, browser journeys, real retrieval and recovery evidence; working cross-repository guides, a credential rotation/recovery owner and named follow-up owners for any explicitly deferred optional surface. A failed required journey keeps the release open.
