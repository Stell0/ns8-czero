## Refined contracts

The following additive details resolve M0's intentionally implementation-level
choices. They do not authorize M2 or change existing content APIs.

- Core producer version is 0.39.0/schema `0033_compilation_state`. The app's
  released Core 0.38 tag, range, lock and patch-only updater remain unchanged.
  The existing explicit producer build generates its own exact local version;
  no fallback or release is introduced. Old-Core consumers omit compiler routes
  and tools. Producer and released-consumer evidence remain separate.
- Existing registry size is 122 operations; M1 adds ten. Its finite capacity
  becomes 160, with a regression for the boundary. Argument/schema limits and
  current role/scope enforcement do not change.
- Source bindings are a closed metadata-only shape: exact logical UUID/revision,
  source and text hashes, provenance hash, ordered-part digest and 1–32 selected
  exact physical chunk identities across at most three documents. The provenance
  digest covers canonical URL and provenance metadata for every physical part; body/part hashes retain
  their existing distinct meanings. Source labels must occur in the originals.
- A read helper computes these bindings from caller-selected current originals;
  another reads indexed dependencies. These are the two additional M1 operations
  below. Neither creates policy, progress, tasks or knowledge.
- M1 dependency rows are **observed proposed support**, not verified compilation.
  Existing target page revisions/hashes and all physical source parts are checked;
  last compiled content and current dependency publication remain M2-owned.
  A source-backed no-change assessment can advance only its explicit source
  assessment marker, with no generated/verified target claim.
- Source state retains bounded current part identities, never bodies. Task
  observations remain at most 16 KiB. This permits multipart freshness checks
  without loading source bodies on status/dependency reads or retaining obsolete
  originals. A changed generation, provenance, part membership or target revision
  makes previous observations stale immediately, without a GET mutation.
- Daily/weekly budget ledgers are internal rows in the existing six-table design's
  runs table. They snapshot IANA window boundaries/caps and retain consumed
  counters. A timezone/cap edit cannot refill an active window. All origins share
  daily limits; weekly work additionally uses the weekly limits. Retried calls
  and reservations keep their debits. Distinct source/target accounting uses
  indexed, immutable event metadata, not another index file or database.
- Work leases use the actor, owner, fence, policy revision, expiry and a trusted
  database-incarnation digest (postmaster start plus current database identity).
  A database restart or clean restore invalidates captured leases without a
  migration backfill or startup job. Reclaim increments the fence; old writers
  and old receipt replays remain denied. This is stricter recovery, not renewed
  authority. Server time is injectable only through trusted Python construction.
- Mutation locking/receipts reuse Core's existing object→knowledge→authority→
  current-content ordering. Compiler events record payload-free audit/usage
  identities; ordinary receipt storage contains only bounded coordinator
  metadata. Raw request keys are hashed into a separate compiler namespace.
- Editor mutations require both Read and Write when consuming source bindings;
  policy configuration requires Admin/Manage and cannot use an API key. Source
  binding reads, status, tasks and dependencies require current Reader/Read.
  Every call requires an explicit space, including Shared.

## M1 interface

All REST routes start `/api/v1/compilation`; all selectors are explicit
`space_id`. MCP has top-level space_id and typed data for mutations. Inputs have
closed fields, bounded identities/hashes/lists and no source bodies, prompts,
model/provider configuration, commands, raw queries or generated answers.

| MCP | REST | Result |
| --- | --- | --- |
| `compilation_policy_get` | GET `/policy` | Disabled defaults/revision zero when absent; no row creation |
| `compilation_policy_set` | PUT `/policy` | Full validated policy replacement with expected revision, enablement reference and replay key |
| `compilation_source_bindings_get` | POST `/source-bindings` (read-only) | Current exact normalized metadata for 1–3 selected logical originals/chunks |
| `compilation_propose` | POST `/proposals` | Deduplicated queued/merged/held/capacity result and actual task identity |
| `compilation_tasks_list` | GET `/tasks` | Bounded filtered keyset page |
| `compilation_tasks_get` | GET `/tasks/{task_id}` | Exact same-space metadata/recovery state |
| `compilation_run_claim` | POST `/runs/claim` | Claim/renew/reclaim one logical run and reserve eligible bounded tasks |
| `compilation_run_checkpoint` | POST `/runs/checkpoint` | Revision-safe fixed task/usage/run observations under the live fence |
| `compilation_status_get` | GET `/status` | Actual bounded run recovery details, counters, source assessment and stale/held coverage |
| `compilation_dependencies_list` | GET `/dependencies` | Indexed reverse-source or target observations and effective freshness |

No `compilation_plan_validate`, `compilation_apply`, `compilation_verify` or
`compilation_discover` operation is installed. No arbitrary operation dispatch.
Checkpoint observations cannot enter M2's applied/succeeded publication states,
accept content bodies, claim complete corpus coverage or promote verification.

A proposal includes expected policy revision, origin (`manual`, `bootstrap`,
`retrieval`, `daily`, `weekly`), closed reason, stable topic key, optional current
page target, exact source bindings and an optional source-derived label. Current
page identity overrides cosmetic topic differences. Exact source-input duplicates
return the retained task; changed support links a successor and supersedes active
older work without erasing its attempts/events. Contradiction/applicability holds
remain reviewable. M1 does not decide semantic equivalence of new topic keys.

Run claims use kind, cycle key, owner, acknowledged policy revision, bounded task
limit and replay key. Daily/weekly new cycles bind the actual local date; an older
stored cycle can resume. Renewal cannot extend the invocation's deadline or
reset task attempts/counters. Independent runs share concurrency and budget rows.

Checkpoints use a closed observation kind, current lease and expected run/task
revisions. They cover proposed plan hash, no-change, retry/defer/failure, model
reservation/start/returned/failed/uncertain, reconciliation and bounded completion.
Reserve before an external call. Started calls become uncertain after lease
transfer; they cannot be replayed as fresh calls. Missing usage retains the full
reserved debit and is reported unknown. M1 performs no model request itself.

Ordinary reads never complete or mutate work. A lost response is reconciled by
actual task/run identities plus the original replay key while its authority/fence
remains valid; after expiry/transfer, read state and explicitly reclaim. Supported
errors are fixed and value-free: invalid request (422), conflict (409), not found
(404), policy/permission/scope denial (403), not-ready source (409), exact expired
content (410), unavailable service (503). Capacity/budget holds are explicit
outcomes with next eligibility, not successful compilation.

## Client sequence and recovery

1. Read `compilation_policy_get(space_id)` and current source/chunk evidence with
   the existing document/context/citation APIs. Read-only use needs no policy row.
2. An explicitly authorized Admin can set the full `data` policy object with
   `expected_revision`, `authorization_ref` and `idempotency_key`. Defaults and
   closed schemas live in [compilation_schema.py](../../packages/czero-core/src/czero_core/compilation_schema.py).
   The enablement reference is hashed, never interpreted as authority. Keys lack
   Manage authority. M1 stores `automatic_supported` only as future policy;
   `publication_supported` remains false in all cases.
3. Read `source-bindings` with `selections` of logical_document_id, revision_id
   and exact chunk_ids. Propose with the returned source_bindings, acknowledged
   policy_revision, origin, reason and stable topic_key; optional target is
   `{kind: page, id, revision, content_id, content_hash}`. Source-derived labels
   are optional. Page IDs normalize cosmetic topic changes. New concepts still
   require an external agent to check existing knowledge; M1 performs no semantic
   deduplication or inference. Terminal repeats retain their actual state.
4. Claim with `data: {kind, cycle_key, lease_owner, policy_revision, task_limit}`
   plus the original replay key. A returned lease is the exact run_id, owner and
   fence tuple. Retain returned run/task revisions. Capacity and budget holds
   are observable outcomes; a claim alone proves no compiled knowledge.
5. Checkpoint with `data: {lease, expected_revision, action, ...}` and replay key.
   Task actions require task_id and expected_task_revision. `planned` additionally
   accepts only plan_hash; no proposed text is stored. `defer`/`fail` take a fixed
   error_code. At the retry limit, both become failed instead of cycling forever.
   `no_change` rechecks original/current target support before assessment.
6. Before an external call reserve_model with task bindings, request_id and
   reserved_tokens (maximum total input/output usage), then start_model with that
   request_id. Return_model records observed_tokens (or null when unknown) and
   external_reference_hash. Fail_model can abandon a known unstarted reservation
   or record a failed started call; debits remain charged. Started interruptions
   become uncertain after takeover; only reconcile_returned/reconcile_failed can
   settle uncertainty. A reservation from an expired day cannot start in a new
   day: abandon it and reserve a new request against current budgets.
7. Finish only when every reserved task is no_change and no model call remains
   unsettled. Otherwise checkpoint partial and resume the same logical run.
   M1 cannot finish a planned publication: its durable plan identity awaits M2.
   Status includes bounded run/call recovery details, effective overdue call
   uncertainty and unknown usage. Complete corpus coverage always remains false.

Read state after any lost response. An identical receipt can replay only while
its source/target authority and captured fence remain current. An expired fence
requires an explicit claim with a new request identity and reconciliation of
saved state. Never turn an uncertain provider call into a fresh request merely
because its lease expired. Source replacement/archival removes eligibility;
status exposes stale identities. Record failure/defer/usage without pretending
expired evidence was rebound. Unsupported evidence remains held for review.

The budget rows are internal, not public runnable cycles. Document/page quotas
count distinct reserved source/target identities. Request/token debits never
refund on retries, lease transfer or unknown usage; observed overages add debit
and block further reservations. Usage is client-reported, not independently
proved provider billing. Readiness and reporting are not scheduling acceptance.

Schema 0033 is additive and forward-only. Back up before any separately approved
real upgrade. A clean restore retains the six tables and receipt/event history;
postmaster/database identity changes invalidate old leases. Read status, reclaim
within retry limits and reconcile uncertain calls. Do not restore by deleting
coordinator or authored knowledge rows. Existing source/Wiki content stays
latest-only and exact retired evidence remains 410.
